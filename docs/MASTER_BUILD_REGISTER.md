## 0. How to read this register

**Hard rule: research is not approval, and approval is not implementation.** Each row carries three separate status fields, and they must be updated independently.

| Field | Allowed values | Meaning |
|---|---|---|
| Proposed | KEEP / ADAPT / BUILD / REJECT / PENDING | The researcher's recommendation only. See mapping below. PENDING also means "evidence is too thin to recommend". |
| Founder status | PENDING / APPROVED / REJECTED / DEFERRED | **Every component row is PENDING.** Only the founder may change this. |
| Build status | NOT STARTED / IN PROGRESS / IMPLEMENTED / VERIFIED | **Every row is NOT STARTED.** Nothing in this register has been built. |

Mapping from the research reports: REUSE = KEEP, MODIFY = ADAPT, BUILD OUR OWN = BUILD, DO NOT USE = REJECT, "evaluate / unreviewed" = PENDING.
KEEP means "adopt as-is after review". ADAPT means "take the code or design with changes". BUILD means "write our own; borrow the idea only".

|---|---|

| V2 | Repository metadata, README, or docs page only. |
| V3 | Inferred from file names or directory listings; contents not read. |
| V4 | Not inspected. Included only because a gap was identified. |

### 0.2 FC-05 detail: what "working MVP" means and does not mean

**Definition.** The MVP is complete only when four functioning agents (Intake, Processing, Quality Control, Reporting) run a request end to end, with each requirement below **verified by running software and recorded evidence, not by documents**:

1. **End-to-end execution:** a synthetic request passes through all four agents, and every handoff is validated against a versioned contract (`work_item.v1`, `candidate_result.v1`, `qc_verdict.v1`, `report.v1`; contract names are still proposals, FND-26).
2. **Authorized tools:** agents call only tools that the runtime allows for that skill and that any required approval has cleared (FND-16, FND-24, FND-07).
3. **Memory:** requests and task state are remembered and conversations can be resumed, within one tenant only.
4. **Security:** users are authenticated and authorized for a tenant, tenants are isolated in the database, personal data is masked before any model call, and secrets are protected.
5. **Audit:** decisions, approvals and completed actions are recorded in a tamper-evident trail (FND-03).
6. **Recovery:** retries, duplicate requests, failures and restarts complete work once, with no duplicates and no silent loss.
7. **Reporting:** the Reporting agent shows business outcomes, performance and exceptions from aggregated data with no personal data.

All 17 platform requirements are in scope. Their status, dependencies, gaps and proposed acceptance criteria are tracked in `docs/blueprint/PLATFORM_MASTER_PLAN.md`; the criteria there are **proposals until the founder approves them**. As of 2026-10-25 none of the 17 is complete, so the MVP is **not** met.

**Completion gate (founder decision, 2026-10-25).** The working MVP requires **all** of the following:
- **R1 exit:** AT-01 to AT-22 pass with founder-set thresholds (`PRD.md` section 6, `DEPLOYMENT_TESTING.md` section 6). Unchanged; no R1 test or gate is added, removed, relaxed or reordered.
- **R2 exit:** PRD-16 to PRD-19 (Processing and QC). Acceptance tests are **not yet written** and must be written and approved first.
- **R3 exit:** PRD-20 to PRD-22 (Reporting, billing and deletion). Acceptance tests are **not yet written** and must be written and approved first.
- **Verified four-agent end-to-end operation** covering items 1 to 7 above.

Thresholds that are TBD (D-04 and others) still block any test that uses them. R4 (PRD-23 to PRD-25) is not part of this gate unless the founder adds it. Some of the 17 requirements touch R4 items (showing outcomes touches RPT-03; approvals touch UI-01); where they do, the founder must decide whether that item joins the gate (conflict C16 in `PLATFORM_MASTER_PLAN.md`).

**Terminology.** In documents written before FC-05, the unqualified word "MVP" means the **R1 Intake pilot**. "Working MVP" means the FC-05 definition above. Where the two differ, FC-05 governs the word "MVP", and the older text is read as describing R1. Where a document's wording could be read as ending the MVP at the Intake tests, it has been changed to say "R1" (`PRD.md`, `DEPLOYMENT_TESTING.md`, `AGENT_SPECS.md`, `ARCHITECTURAL_ESSENTIALS.md`).

**R1 is preserved.** The Intake pilot (shadow mode, synthetic data, one channel, `PRD.md` R1, D-13) keeps its definition and remains the first gate. The `PRD.md` section 7 out-of-scope list describes R1 and is not rewritten. Processing and QC (PRD-16 to PRD-19, R2) and Reporting, billing and deletion (PRD-20 to PRD-22, R3) are already roadmapped there; their acceptance tests are **not yet written** (`PRD.md` lines 103-104) and must exist before the MVP can be called complete.
