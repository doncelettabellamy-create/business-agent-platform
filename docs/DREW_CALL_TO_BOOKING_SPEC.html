5. Remembered answers, skip and retry rules

5.1 What the call remembers

  • One Intake pass runs over all the caller's words after every turn, so an answer given early, or out of order, fills its field and that question is never asked BUILT.
  • Names, numbers and addresses are masked before any text model reads them; the raw values live in the call's memory and then in the encrypted contact vault (30-day pilot retention) BUILT.
  • The caller's correction ("actually three bedrooms") replaces the earlier answer because the pass reads the whole conversation BUILT.

7. Approved pricing (SIMULATION only)

SIMULATION There are no business-approved rates. The only pricing in existence is a test fixture (pricing-fixture.ts, BUILT, not connected to the phone or to Processing). It is test data and says so on every result.
  • The fixture's single rule: a standard cleaning of a house or apartment with at most 2 bedrooms and 2 bathrooms is $199.99, less a $25.00 first-clean discount, giving $174.99. It is a test rule, not a rate card, and not the business's.
  • A price is given only when everything is known and eligible: details confirmed, the first-clean answer is yes, service and property type are the ones the rule names, bedrooms and bathrooms are within limits, no extras, not commercial. Anything else is "a person will price this", with a reason code and no number. Nothing is guessed, rounded or estimated.
  • Quote versus estimate (firm price vs range vs person always prices) per service: UNDECIDED. With no policy set the only allowed words are "a person will price this".
  • The special and the fixture: the greeting's "$25 off a qualifying first standard cleaning" and the fixture's $25 first-clean discount are separate things today. Whether they are the same offer is UNDECIDED.
  • Who approves real rates, and when LIVE begins: UNDECIDED (roadmap section 6 item 2).

When a simulated price is spoken, the server supplies the exact words, including that it is simulated:

This is a simulated quote for testing, not a real price. For a standard cleaning the simulated price is one hundred seventy-four dollars and ninety-nine cents, including a twenty-five dollar first-cleaning discount. Would you like to hear simulated appointment times?

Wording is a proposal. If no price applies: "A person will need to price this, so I can't give a price on this call." A promise that anyone will call back is not made unless the business has a callback process and a stored number (roadmap section 3a).

9. Customer approval and verified booking

  1. Customer approval. A price or a booking is final only after the customer has heard it in fixed words and said an explicit yes. A vague, unclear or missing answer is not approval. BUILT for the read-back confirmation; MISSING for quote and appointment approval.
  2. Business approval. Where the business wants a named human to approve anything with money or a commitment, Processing pauses for that approver BUILT (mock tools). Which items need a human is UNDECIDED.
  3. Write once. After approval, one booking write with a single idempotent key. A repeat or retry returns the first result and makes no second write. BUILT as a Processing mechanism (step ids); MISSING for a booking tool.
  4. Verify by an independent read. QC reads the calendar entry, the quote and the contact on file with its own readers, not from the Processing result, and compares. A match is a verified booking; anything else is reported as not booked and escalated to a person. BUILT against mock evidence readers; MISSING against a calendar.
  5. Only then the customer is told it is booked. Server-supplied wording, marked simulated while in SIMULATION:
Your simulated appointment is confirmed for Tuesday the twelfth of March at nine in the morning. This is a test booking, not a real appointment. Goodbye.

If any step fails, the assistant says nothing it cannot back, stops quoting and booking, hands the request to a person as unconfirmed with the reason recorded, and does not promise a callback unless a callback process exists.

10. Native Realtime conversation with controlled server tools (design)

Today the OpenAI voice only speaks exact words the server gives it, and a separate text model plus Intake decide what to ask (BUILT, "Option A"). The proposal is to let the Realtime voice hold the conversation natively (listen, understand, answer small side questions, sound natural) while the server keeps every decision that matters behind a small set of tools. The model can only request a tool; the server runs it, validates the arguments, and returns a result the model must voice.

10.2 What stays outside the model

  • Prices, slots, dates and confirmations are spoken only from tool results; the model has no figure of its own and no tool for a price the table does not give.
  • Consent, limits, emergency line, kill switch, masking, contact vault, record saving, and the dashboard allow-list stay in server code.
  • Tool arguments are checked against the skill's field list and the issued ids; a call the model invents is refused and logged as a fixed code.
  • Tool results carry no customer text beyond what must be said; logs hold fixed codes and numbers only.

10.3 Not decided, and the risks to settle first

  • UNDECIDED Whether to move from Option A (server picks every question, voice only speaks) to native tool calling at all. Native is more natural but gives the model more room to drift; the tools above constrain it but need testing for repeats, interruptions and spoken-number accuracy.
  • UNDECIDED Whether the voice model or the text model extracts answers (today: Intake on the text model). Using Realtime function calls would send the caller's raw words to OpenAI's voice model, which already hears the audio; masking before a text model would no longer apply to that path.
  • MISSING Consent-before-audio, the interrupted-read-back gap and the two masker gaps remain open (roadmap section 6 item 11).
  • Model, voice and reasoning settings are already chosen for the founder test (founder-voice.config.json) and are not changed here.
