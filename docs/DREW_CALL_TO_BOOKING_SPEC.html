5A. Current-call state: how answers enter it, and why they stay "missing" or repeat

Read-only code review of pii-screen.ts, contact-capture.ts, call-session.ts, next-field.ts, relay-handler.ts and dialogue-model.ts (2026-10-27). Nothing was changed. "Current-call state" below is what one live call holds in memory and discards at hang-up. It is not long-term memory and it is not the agent hand-off (both in section 5B).

5A.1 State flow for one call (as built)

  1. Every caller utterance is masked by rules; it is refused if odd or if anything personal-looking is left (the whole call then ends with the fixed apology).
  2. Only the masked line goes to the Intake pass and to the dialogue history. The raw value is kept per placeholder in memory.
  3. Intake re-reads every masked line each turn and reports the cleaning fields found and missing.
  4. Name, number and address do not come from Intake or from the question asked. They are looked up from the masker's detections by extractContact each turn.
  5. The next question is chosen from Intake's missing fields plus any contact item still undetected.

9. Customer approval and verified booking

  1. Customer approval. A price or a booking is final only after the customer has heard it in fixed words and said an explicit yes. A vague, unclear or missing answer is not approval. BUILT for the read-back confirmation; MISSING for quote and appointment approval.
  2. Business approval. Where the business wants a named human to approve anything with money or a commitment, Processing pauses for that approver BUILT (mock tools). Which items need a human is UNDECIDED.
  3. Write once. After approval, one booking write with a single idempotent key. A repeat or retry returns the first result and makes no second write. BUILT as a Processing mechanism (step ids); MISSING for a booking tool.
  4. Verify by an independent read. QC reads the calendar entry, the quote and the contact on file with its own readers, not from the Processing result, and compares. A match is a verified booking; anything else is reported as not booked and escalated to a person. BUILT against mock evidence readers; MISSING against a calendar.
  5. Only then the customer is told it is booked. Server-supplied wording, marked simulated while in SIMULATION:
Your simulated appointment is confirmed for Tuesday the twelfth of March at nine in the morning. This is a test booking, not a real appointment. Goodbye.

If any step fails, the assistant says nothing it cannot back, stops quoting and booking, hands the request to a person as unconfirmed with the reason recorded, and does not promise a callback unless a callback process exists.

10. Native Realtime conversation with controlled server tools (decided direction; tool design open)

Decided by the founder: Drew converses natively on Realtime. Today the OpenAI voice only speaks exact words the server gives it, and a separate text model plus Intake decide what to ask (BUILT, "Option A"). The direction is to let the Realtime voice hold the conversation natively (listen, understand, answer small side questions, sound natural) while the server keeps every decision that matters behind a small set of tools. The model can only request a tool; the server runs it, validates the arguments, and returns a result the model must voice.

Checkpoint (2026-10-27): the contact part of native conversation is built, offline. An opt-in voice setting (conversation: "native", default scripted) lets the voice converse in its own words with exactly five server-validated contact tools (collect name, phone, address; correct contact; call status). Every call is validated, answered with labels only, and refused when unknown. BUILT and tested against an offline model; MISSING any live trial, and every tool below that is not a contact tool (quote, slots, booking, hand-off). Contract change: the voice service keeps the call's turns during a native call. See roadmap section 5a-3.

15.2 Verified: Twilio behaviours the design relies on (Twilio docs, read 2026-10-27)

  • <Connect><Stream> is bidirectional; later TwiML does not run until the server closes the WebSocket, after which the remaining TwiML resumes. A stream can also be ended by updating the call with new TwiML through the REST API.
  • <Connect> has action and method: "when the Connect verb ends, Twilio sends an HTTP request to this URL".
  • <Stream> takes only wss; the URL does not support query strings; custom data goes in <Parameter> (under 500 characters per name and value together).
  • <Gather input="speech"> posts SpeechResult (and Confidence) to action; supports speechTimeout, timeout (default 5), hints and actionOnEmptyResult; a <Say> nested inside can be interrupted by the caller.

15.4 Proposal: consent before any audio reaches OpenAI PROPOSAL

  1. Twilio's incoming-call webhook (signature-checked, as now) returns <Say> with the exact notice (Drew's introduction, the special, the OpenAI disclosure), then <Gather input="speech" action="/consent" actionOnEmptyResult="true">. Keeping the notice outside the Gather means it cannot be talked over; a nested Say can.
  2. The /consent webhook (signature-checked) applies the existing yes-and-not-no rule to SpeechResult, and writes the CallSid to an in-memory consent ledger. On yes it returns <Connect><Stream>; on no, silence or anything else it returns a <Say> goodbye and <Hangup>.
  3. When the stream opens, the call logic refuses any CallSid with no ledger entry (fail closed; a second factor beside the secret path and signature).
  4. The caller's yes or no is heard by Twilio only. Consent-before-audio, an open gap today, is closed. This is independent of GPT-Live and also works with the current engine.
  5. The notice is read in Twilio's voice, not Drew's marin voice (persona difference accepted for now; pre-rendered audio is a later option).

15.5 Proposal: read-back and confirmation during the call PROPOSAL

  1. GPT-Live converses (full duplex). It reports what it hears through validated tools (the five contact tools; the server validates every call) and may call call_status and a gated begin_confirmation. The server also gives it captured and missing field names as unspoken context (session.thinking.append), never as commands to speak.
  2. begin_confirmation succeeds only when consent is on record, Intake is ready, the contacts are captured, and the residential question is settled. Only then does the server act.
  3. The server lets the model finish its sentence, closes the stream (after the close handshake) and Twilio resumes the TwiML: a <Say> with the exact read-back (job, name, callback number) and <Gather input="speech"> for yes or no; on yes, the address read-back the same way; on yes again, thanks and <Hangup>. Exact words stay exact (they are Twilio's text-to-speech, not the model's).
  4. On no, a new GPT-Live session is opened, seeded with the masked history through session.start's input, told that the caller wants to change something, and the cycle repeats within the existing limit of two read-backs.
  5. Limits and the clarification bound are enforced by the server ending the stream, not by scripted questions.
  6. Alternative, unproven: let GPT-Live speak the read-back, buffering its audio, checking its transcript against the text, and releasing or discarding it (OpenAI's own suggestion).

Costs, stated: the read-back is in Twilio's voice; the raw name, number and address travel in the TwiML to Twilio and may appear in Twilio's request logs (acceptable for invented details; real customers need a data decision); the call logic currently treats a repeated CallSid as a replay and needs a resume case; the voice-side context after a restart is only the seeded masked history.

15.6 Proposed build order (each step separately approved) PROPOSAL

  1. Twilio consent webhook and ledger (offline-tested; independent of GPT-Live; closes consent-before-audio).
  2. GPT-Live dialect adapter at the link seam, with an offline stand-in and tests, behind a voice-config engine setting that defaults to the current engine.
  3. Live-call orchestrator reusing the call state, tools, masker and Intake; record saving is inside relay-handler's finish() and would first be extracted (a mechanical refactor of tested code).
  4. Twilio confirmation leg with stream resume.
