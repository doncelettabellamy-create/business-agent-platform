What exists, in layers (all synthetic-only, mock-tested, in memory):
1. **Tenant boundary** (`tenant-boundary.ts`): a tenant-keyed, deep-frozen, runtime-read-only config registry; the message must carry the context's `workspace_id`; config and classification keys are refused; the message is read once; refusals happen before any provider call; a result naming another tenant is refused. It now requires a **minted** context for the `intake` agent that holds the explicit scope `intake:run`.
2. **Execution context** (`execution-context.ts`): minted from an injected verifier, tenant selector and grants; frozen, one tenant, recognized by identity (copies, clones, JSON and proxies are rejected); default-deny `can()`; narrowing only; `acceptHandoff()` is the receiver-side tenant check for Processing.
3. **Controlled entry** (`intake-entry.ts`): provider, registry, channel, clock and limits are fixed at setup; sender input is allowlisted; correlation id, time and channel are platform-owned; only explicitly synthetic records are accepted; request-time failures never throw.
4. **Live developer path** (`live-run.ts`, `reviewed-fixtures.ts`, `live-entry.ts`): only four pinned synthetic fixtures (canonical-digest pinned) can be sent; developer authority is minted from fixed mock sources; the raw runners are no longer called from `live-entry.ts`.

5. **Observability** (`observability.ts`): a vendor-neutral allow-list emitter that stamps tenant, correlation id, agent and actor kind from a minted context; fixed event vocabulary; no customer text or configuration names; one 8-class failure taxonomy over all 27 codes; best-effort telemetry kept apart from a separate mandatory-audit path that reports failure instead of hiding it. It has no real sink and is not wired into the entry or the runners.

Known residual risks: the raw runners and the boundary functions remain public exports (an inventory test only detects new importers); `cli.ts` and `demo.ts` still call the raw runners on the sender's tenant and config; `runReviewedLive` does not itself enforce the live flag or environment gate, and no test pins who may import `live-run.ts`; whoever supplies the sources to `mintExecutionContext` defines what a context means; the registry check is by shape; the `owned()` post-check has no direct test; no timeout on minting sources; the digest table is the only review step.

## 5. The 17 components

Acceptance criteria are **proposals**, not founder-approved. "AT-nn" refers to the acceptance tests mapped in `PRD.md`; they are listed in `DEPLOYMENT_TESTING.md` for the Intake pilot only. Criteria without an AT number have no existing test definition.

### 1. Authentication — Verify who is accessing the platform
- **Verified status:** **Not started.** `ARCHITECTURE.md` section 6 says "Managed auth (TBD) with MFA for admins (TBD)". The PoC authenticates no one; the tenant boundary assumes the caller derives its `TenantContext` from verified authentication (stated in its header comment).
- **Dependencies:** FND-01 decisions; FND-10 secrets; a managed-auth choice (TBD); FND-12 rate limiting.
- **Missing work:** choose and integrate an identity provider; sessions; MFA for admins; machine credentials for channels and workers; a verified link from authenticated identity to `TenantContext`.
- **MVP acceptance criteria (proposed):** an unauthenticated request reaches no tenant data and no agent; an expired or forged credential is rejected and recorded without request body; admin accounts require MFA (TBD); credentials never appear in logs, traces or errors (AT-11).

### 2. Tenant authorization — Verify which business they can access
- **Verified status:** **Partly built in PoC (committed in c7af9de), and only for the tenant-to-config step.** The registry maps a tenant to its own config, and the message must match the trusted context. **No user-to-tenant membership or role model exists.** Unverified whether any production shape of membership is planned beyond `DATABASE_DESIGN.md`.
- **Dependencies:** component 1 (identity); FND-02 (workspace model); FND-07 (approver identity, Later); D-08 (who approves what).
- **Missing work:** membership and role tables; deriving `TenantContext` from membership; per-action authorization; testing against the real identity source; the D3 decision.
- **MVP acceptance criteria (proposed):** a user of tenant A cannot select tenant B by any request field (AT-04, extended to users); an unregistered tenant is refused with no fallback config; a user with no membership gets a refusal, not an empty result; every refusal is recorded (component 11).

### 3. Tenant isolation — Prevent businesses from accessing each other's data
- **Verified status:** **Built in PoC at the application layer only (committed in c7af9de)** (frozen per-tenant config, snapshot admission, ownership check on results; mock tests show no cross-tenant leakage to a shared provider). **Database isolation is not started** (FND-02, forced row-level security, restricted role, CI scoping guard FND-25).
- **Dependencies:** FND-02, FND-25, FND-22; component 13 (storage).
- **Missing work:** Postgres forced RLS with a restricted runtime role; startup refusal under a bypass-capable role; CI guard that every query is tenant-scoped; cross-tenant tests against a real database; making the boundary mandatory for all entry points.
- **MVP acceptance criteria (proposed):** AT-03 and AT-04 pass against a real database; app-only isolation is not accepted as the sole mechanism (`ARCHITECTURAL_ESSENTIALS.md` section 5 rule 2); no entry point can call the runners without the boundary.

### 4. Communication — Voice, chat, email, SMS, and other channels
- **Verified status:** **Not started.** The PoC accepts only an already-masked JSON record; no channel code exists. `PRD.md` allows **one TBD channel (D-02)** for the pilot and puts customer replies and outbound actions out of scope. No voice or SMS design was found in the docs I searched (unverified beyond that search).
- **Dependencies:** D-02; INT-01, INT-02, INT-03, INT-04; FND-04 (dedupe); FND-12; components 1, 3, 15.
- **Missing work:** per-channel adapters with signature or secret verification and replay windows; acknowledgement timing; normalisation to the inbound record; outbound path with approval (component 8); voice and SMS are undesigned.
- **MVP acceptance criteria (proposed):** at least one real channel passes AT-05, AT-06, AT-07; forged, unsigned or stale requests are rejected and audited without body; each additional channel (voice, SMS, email, chat) needs its own register row and founder decision before it counts toward the MVP.

### 5. Conversation memory — Remember requests and resume conversations
- **Verified status:** **Not started.** The runners are stateless: one message in, one work item out. No conversation or thread concept exists in the contracts. Pause/resume is "Later" and undecided (FND-05, D-05). The Orchester memory service (Mnemosyne) is excluded by the register.
- **Dependencies:** component 13; FND-05, D-05; FND-23 (run scopes); component 15 (masked-only storage).
- **Missing work:** a conversation model (threads, turns, per-tenant scoping); what may be remembered and for how long (no register decision on retention, C14); resume semantics; a rule that stored context stays masked.
- **MVP acceptance criteria (proposed):** a second message in the same conversation is linked to the first within the same tenant only; a conversation cannot be read or resumed across tenants; stored context contains no raw personal data (AT-08/AT-11 extended); resume after a restart does not duplicate work (AT-22).

### 6. Agent orchestration — Coordinate Intake, Processing, QC, and Reporting
- **Verified status:** **Only Intake exists, and only as a PoC.** `agents/intake/` has `AGENT.md` and four skill folders; `agents/processing`, `agents/quality-control` and `agents/reporting` **do not exist** (checked by listing `agents/`). The Intake → Processing handoff envelope (`work_item.v1`) is built and validated in the PoC. There is no Processing receiver, no `candidate_result.v1`, `qc_verdict.v1` or `report.v1`, no worker, queue, or engine choice (PRC-01, D-05).
- **Dependencies:** FND-26, FND-14, FND-08, FND-05/D-05, PRC-06, QC-01, RPT-02, D-06, D-01.
- **Missing work:** three agent folders and specs; three contracts; a runtime that loads skills (FND-14); workflow engine decision; handoff rules and loop limits (QC rework, D-06); audit event per handoff.
- **MVP acceptance criteria (proposed):** exactly four agent folders (AT-01); a synthetic request flows Intake → Processing → QC → Reporting with each handoff validated against a versioned contract and an unsupported version rejected (AT-20 extended); QC cannot edit the candidate; a loop limit stops rework (D-06).

### 7. Tool integrations — Connect to approved business applications
- **Verified status:** **Not started.** No integration is approved or named (D-01, D-02 undecided; `PRD.md` section 7 puts integrations out of scope). The Intake PoC has no tools by design; the only external call is the gated model provider.
- **Dependencies:** D-01, D-02; FND-16 (tool gateway); FND-10 (injected secrets); FND-04 (idempotency); PRC-04; component 8.
- **Missing work:** a tool gateway with an allow-list; adapters; secrets injected, never held by agents; idempotent writes (crash recovery repeats steps); the list of "approved" applications is itself undecided.
- **MVP acceptance criteria (proposed):** an agent can call only tools on its skill's allow-list as enforced by the runtime, not by the skill's own declaration; a prompt-injection fixture triggers no tool call (AT-17); a repeated step makes no duplicate external write; no integration is added without a register row and founder approval.

### 8. Permissions and approvals — Control what agents can read, change, or execute
- **Verified status:** **Not started.** The PoC limits what the model sees (masked text, category and field names only) and requires explicit flags for live calls; neither is an agent permission system. Approver identity, run scopes and per-tool approval flags (FND-07, FND-23, FND-24) are designed or borrowed ideas only.
- **Dependencies:** components 1, 2; FND-07, FND-16, FND-23, FND-24; D-08.
- **Missing work:** permission tiers per skill; approval records bound to approver identity, role, tenant and action; decline reasons; expiry; a rule that holding a run id never grants approval.
- **MVP acceptance criteria (proposed):** an action above its permission tier waits for an authorised approver; an approval by someone outside the tenant or role is refused; approvals are checked against a server-side record, not the client's message; every approval and refusal is audited (component 11).

### 9. Logging — Record errors and operational events
- **Verified status:** **Not started.** No logger exists. The PoC scripts print codes and counts with `console.log`/`console.error`. Typed error codes exist (runner, model gateway, boundary). `DIAGNOSTIC_LOGGING.md` is a draft with a field list, event vocabulary and the "no bodies, no raw values" rule.
- **Dependencies:** FND-19 (register verification level **V4**: its source path is unverified); component 15; retention and storage (no register decision, C14).
- **Missing work:** an allow-list emitter that drops unknown fields and free text; tenant stamping from trusted context only; failure classes; wrapped third-party exceptions; retention and access roles (TBD).
- **MVP acceptance criteria (proposed):** AT-11 passes after the whole suite including forced failures; LOG-T1 (one correlation id per item), LOG-T2 (forced failures log a code and no content); a failing log sink never changes a run result.

### 10. Tracing — Track requests across agents and tools
- **Verified status:** **Partly built in PoC.** The result carries a per-skill `trace` (source, provider id, attempts, failure code), and `correlation_id` is copied into the handoff envelope. There are no spans, no timings, no trace or span ids, and nothing propagates across agents or tools. `OBSERVABILITY.md` is a draft.
- **Dependencies:** component 9; the envelope contract; correlation id ownership decision; tooling (undecided; FND-19 is V4).
- **Missing work:** correlation id minted by the platform, not the sender; a trace/span field in the envelope (contract change); propagation through the queue, runs, tool calls and model calls; span attributes limited to ids, enums, counts, durations, versions.
- **MVP acceptance criteria (proposed):** OB-T1: one correlation id appears in every span and log line of an item across all four agents; spans contain no bodies or raw values (AT-11); a replayed or re-run step is marked as such.

### 11. Audit trails — Record decisions, approvals, and completed actions
- **Verified status:** **Not started.** The runner states it has no audit chain (header of `intake-runner.ts`). `FND-03` (hash chain) is ADAPT, PENDING, and the reference was only partly read (V1 for `chain.ts`; the verification job is V3).
- **Dependencies:** FND-02, FND-03, FND-08 (verification job), components 3, 13; D-09; retention (no register decision, C14).
- **Missing work:** append-only, hash-chained table with serialised appends; handling of odd value types; chain head anchored outside the database; scheduled and on-demand verification; the rule that a failed audit append blocks the state change; retention versus erasure.
- **MVP acceptance criteria (proposed):** AT-15 (an altered row is detected; concurrent appends do not fork the chain); every state change, approval and handoff writes an audit event in the same transaction; audit metadata contains no raw values (AT-11); audit is never sampled.

### 12. Monitoring and alerts — Detect failures, unusual activity, and service problems
- **Verified status:** **Not started.** `OBSERVABILITY.md` is a draft signal catalog, severity routing and runbook headings. Thresholds, SLOs, tooling and on-call are TBD. The PoC computes no metrics.
- **Dependencies:** components 9, 10, 11; FND-08 (verify job); D-04. No register row covers service monitoring or alerting (see section 7).
- **Missing work:** metrics, health and readiness checks, alert routes, runbooks (headings only), canary item; safety alerts on any cross-tenant failure, raw-value leak or audit tamper.
- **MVP acceptance criteria (proposed):** OB-T2 (each safety condition, deliberately triggered, raises an alert); a canary item completes within a target time (OB-T3; target TBD); the service refuses to start under a bypass-capable database role (AT-03).

### 13. Durable storage — Preserve authorized business data and task state
- **Verified status:** **Not started for the platform.** The PoC is in-memory: results are returned and nothing is persisted. The registry is in memory. `prototype/intake-work-items/` holds static front-end files (I did not re-read their contents; whether they carry only synthetic data is **unverified**). `DATABASE_DESIGN.md` is a draft.
- **Dependencies:** D-14 (TypeScript + Postgres, proposed), FND-02, FND-22, INT-08 (vault), FND-10.
- **Missing work:** schema and migrations; tenant-scoped tables with forced RLS; work-item and task-state storage; an encrypted vault for raw values; backups and restore; retention and deletion/export (FND-13, Later).
- **MVP acceptance criteria (proposed):** a work item survives a restart (AT-22); data of one tenant cannot be read by another through any path (AT-03); no plaintext raw values at rest (AT-10); restore from backup is tested.

### 14. Reliability — Handle retries, duplicate requests, failures, and recovery
- **Verified status:** **Partly built in PoC.** Verified: bounded retries and a timeout in the model gateway, fail-closed fallback to `needs-human` on model failure, a deterministic item id from workspace and event id (so the same event maps to the same id), and tests for these using mocks. **Not built:** a queue or worker, a dedupe store, crash recovery, a poison-item rule, rate limiting. D3 (throws escaping the boundary) is open.
- **Dependencies:** FND-04, FND-08, FND-12, FND-17; component 13; D3 decision.
- **Missing work:** idempotency keys stored per tenant; a job runner with graceful shutdown; parking of refused or errored messages instead of dropping them; recovery that marks re-runs; provider outage handling (RB-02) and runbooks.
- **MVP acceptance criteria (proposed):** duplicate delivery yields one work item (AT-06); killing the process mid-run leads to completion once or a retry with no duplicate (AT-22); a model or detector outage parks the item as `needs-human` with no unmasked call (AT-13); no accepted message is silently lost.

### 15. Security and privacy — Protect secrets, sensitive information, and customer data
- **Verified status:** **Partly built in PoC, synthetic data only.** Verified in code and tests: the model receives masked text plus category and field names only; extracted values must be grounded in the text; error and validation messages use fixed text; the live path needs explicit gates (`INTAKE_ALLOW_LIVE_CALLS` and flags).
